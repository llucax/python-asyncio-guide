New structure proposal:

Tio's docs are great, but I think the structure didn't map as well for this guide. I feel we ended up with a lot of duplication and overlap. I want to restructure this guide with the goal of having more orthogonal sections, introducing concepts one by one in layers instead of mentioning many concepts with one focus to then mentioned them again with a different focus.

I propose the following chapters instead of the current tutoria + core appoach:

* Everyday asyncio: how to write realiable and effective asyncio programs, only introduces the safe APIs, it doesn't mention low level APIs, like create_task() or wait_for() at all. Not sure if this chapter should include an advanced usage section that includes more advanced topics like shielding. I'm not sure if there are valid use cases for shielding when writing simple asyncio programs if the used libraries are well designed and robust. Please make a judgement call on this one. This section must include the basic constructs, like TaskGroup, run(), timeout(), sleep(). There could be a section on other high-level tools, like synchronization primitives, queues, etc. But more like an appendix/index, mainly pointing to the official docs and giving some examples where the official docs fall short. A section on debugging should also be included here, but again only covering the safe APIs. Cancellation should be definitely covered here, in particular in the context of task groups and timeouts.
* Understanding how asyncio works: Introduces more low level concepts, the building blocks to build the abstractions explained in the first part, ideally explaining how those abstraction are built from these basic building blocks when possible, but doesn't get into more advanced topics that don't serve this purpose (for example, no need to mention shielding). It should not include other tools that are not used as building blocks for the main abstractions. cancelling(), uncancel() and the counter should be mentioned in this section only if it serves to explain how taskgroup cancellation or timeouts are implemented.
* Advanced asyncio tools: Mention more dangerous and niche asyncio APIs that can be used when building frameworks or asyncio utility libraries, here for sure should be a mention of shielding if it was not mentioned or explained in detail before. If there are debugging tools specifically for APIs only explained here, we should also include a debugging section here with the specifics for those APIs. Don't mention deprecated APIs even here, if there is known Python version where something got deprecated, and the new recommended replacement for that API is present in Python 3.11+, then just completely skip the deprecated API and explain/mention only the new one. Same for overlapping APIs, for example I'm not sure if there is a place for gather(), it feels like advace usages should just go for "wait()", but I might be wrong. Please use your judgement to asses if some API should not be mentioned at all. We don't need to cover absolutely all the available APIs, there are the official docs for that.
* Apendix: Stuff that is good to have as reference should go here, for now I can only think about the checkpoint contract table, but maybe there is already more stuff we can put in here. Another appendix might be a comprehensive list of common recommendations, best practices, pitfalls and gotchas, like awaits inside finally blocks, using aclosing() for async generators, etc. Another appendix could be a comprehensive list of debugging tools and techniques (if there are spread accross different chapters).

Here is an analogy with git to better express what I expect to go on each chapter:
* Everyday git: tells about git init, add, commit, push, pull, branch, merge, rebase, etc. It doesn't mention low level concepts like DAGs, blobs, trees, refs, etc. It doesn't mention plumbing commands at all.
* Understanding how git works: explains how git stores commits, branches, etc. under the hood, but doesn't mention plumbing commands at all.
* Advanced git tools: explains plumbing commands and how to use them to build custom tools. It also explains how to use plumbing commands to do advanced stuff that is not possible with porcelain commands, like rewriting history,

Ideally an user should be done after reading the first chapter, they should have all the knowledge needed to write any Python async program in a robust and safe way (in this sense I guess an advanced section that covers shielding, to_thread() and maybe others, makes sense, as I guess there are valid use cases in programs that are designed in a way to work well with structured concurrency; maybe the advanced section should be recipe based, like "if you need to call blocking code that doesn't take the GIL, use to_thread()" and explain, "if you need to run blocking code that takes the GIL, use run_in_executor()" and explain, "if you need to make sure a block of code is not cancelled, use shield" and explain, etc.). But this chapter should not expose them AT ALL to unsafe APIs that have a safe alternative. For example, a reduced checkpoint contract table should also be in this section, because they are necessary to write robust and cooperative async code, but it should only include the safe APIs explained in this chapter and link to the full table for reference. When it comes to cleanup, mention async context managers and aclosing() as the main tools, mention try/finally should be only used when a async context manager is not available. We probably should include an explanation and example on how to build an async context manager in the advanced topics/recipes section in this chapter.

Only if the user wants to have a deeper understanding of how things work under the hood, they should need to read the second chapter. This chapter can (and should) introduce unsafe APIs, but only when they are necessary to explain how things work under the hood and how safe APIs are implemented. For example, the loop should be introduced here (the first section can mention the loop as a concept, but not mention the APIs), with the basic functions to explain the execution model. But there is probably no need to mention get_running_loop() here.

Only if the user wants to implement advanced asyncio tools or frameworks, they should need to read the third chapter, where we can mention more dangerous APIs that are not necessary to understand how things work under the hood, but are necessary to build advanced tools and frameworks. For example wait_for(), wait(), all_tasks(), current_task(), get_running_loop(), etc.

In the current structure, it feel some topics are covered many times, like cancellation (what happens if a CancelledError is swallowed), checkpoints, asyncio being cooperative. In the new structure I would like topics to be explained only once (of course a few exceptions when a concept can be casually mentioned but not explained in detail will be necessary, specially in the everyday chapter). I want you to think on a good reading flow that minimizes the need to repeat concept explanations.

My feeling is the everyday asyncio chapter will be the longest one by far, as it probably needs to include also sections about streams (async iterators), async generators, proper cleaup, etc. But this is fine, although please consider the option of having the everyday asyncio chapter actually split in 2, everyday basics and everyday advanced (so basically make the advanced usage section a separate chapter, and maybe name the "Advanced asyncio tools" differently to emphasize the difference, maybe something more like "Building asyncio tools" or something like that, please think about chapter names and make proposals for different options that could play together well).

Please go through all the available asyncio APIs and decide in which section each should be introduced.

Even when I want to probably diverge considerably from Trio's docs structure, I would like to keep the same tone and style.
